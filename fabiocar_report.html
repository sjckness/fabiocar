3. Nodes

vesc_driver — vesc_driver.cpp

Low-level binary-protocol driver to a Vedder VESC over USB serial. 50 Hz telemetry poll.

  • Subscribers (all std_msgs/Float64): commands/motor/duty_cycle, commands/motor/current, commands/motor/brake, commands/motor/speed (eRPM), commands/motor/position (rad), commands/servo/position (0–1)
  • Publishers:
    • sensors/core — vesc_msgs/VescStateStamped
    • sensors/imu — vesc_msgs/VescImuStamped
    • sensors/imu/raw — sensor_msgs/Imu
    • sensors/servo_position_command — std_msgs/Float64
  • Parameters: port, plus min/max clamps for duty_cycle / current / brake / speed / position / servo

ackermann_to_vesc_node — ackermann_to_vesc.cpp

  • Sub: ackermann_cmd (AckermannDriveStamped)
  • Pub: commands/motor/speed, commands/servo/position (Float64)
  • Params: speed_to_erpm_gain/offset, steering_angle_to_servo_gain/offset

vesc_to_odom_node — vesc_to_odom.cpp

Bicycle-model dead-reckoning integrator.

  • Sub: sensors/core (VescStateStamped), sensors/servo_position_command (Float64)
  • Pub: odom (nav_msgs/Odometry); optional /tf (odom→base_link)
  • Params: odom_frame, base_frame, publish_tf, use_servo_cmd_to_calc_angular_velocity, speed_to_erpm_gain/offset, steering_angle_to_servo_gain/offset, wheelbase

ackermann_mux — ackermann_mux.cpp

  • Sub: dynamic list from topics param (each AckermannDriveStamped) and locks param (each std_msgs/Bool)
  • Pub: ackermann_cmd_out (AckermannDriveStamped) — remapped to ackermann_drive in bringup_launch.py:121
  • Params: topics, locks lists (each with topic, timeout, priority)

throttle_interpolator — throttle_interpolator.py

Rate-limits motor RPM and servo commands at 75 Hz.

  • Sub: commands/motor/unsmoothed_speed, commands/servo/unsmoothed_position (Float64)
  • Pub: commands/motor/speed, commands/servo/position (Float64)
  • Params: max_acceleration, speed_max/min, throttle_smoother_rate, speed_to_erpm_gain, max_servo_speed, steering_angle_to_servo_gain/offset, servo_smoother_rate, servo_max/min
  • Note: commented out in bringup (line 136)

urg_node (external — urg_node apt package)

  • Pub: /scan (sensor_msgs/LaserScan)
  • See §7 for Hokuyo config

5. VESC Package Deep-Dive

Interface: USB serial via serial_driver (asio-based, 115200 baud, port from port parameter; default in config: /dev/sensors/vesc). Binary framing with SOF 0x02 (small) / 0x03 (large) and CRC; parsed by VescPacketFactory.

Commands sent to VESC (subscriber → outbound packet):

ROS topic (Float64)VESC command
commands/motor/duty_cyclesetDutyCycle
commands/motor/currentsetCurrent (A)
commands/motor/brakesetBrake (A)
commands/motor/speedsetSpeed (electrical RPM)
commands/motor/positionsetPosition (rad → deg)
commands/servo/positionsetServo (0..1)

Feedback published (50 Hz poll of requestState + requestImuData):

  • sensors/core (vesc_msgs/VescStateStamped): voltage_input, current_motor, current_input, duty_cycle, speed (eRPM), temp_fet, temp_motor, charge/energy counters, fault_code, displacement
  • sensors/imu (vesc_msgs/VescImuStamped): roll/pitch/yaw, linear_accel, angular_vel, compass, orientation quaternion
  • sensors/imu/raw (sensor_msgs/Imu): same as above in standard ROS form
  • sensors/servo_position_command (Float64): echo of the last commanded servo position

Driver state machine: INITIALIZING → requestFWVersion → on FW response → OPERATING (timer polls telemetry).

6. MPC Controller Deep-Dive

The "production" controller is frenet_mpc_node (frenet_mpc_node.py). It is the only one whose parameters are declared as ROS parameters (i.e., tunable) and is the node name (/frenet_mpc_controller) targeted by the LLM tuner.

Formulation:

  • State (per step k): [x, y, yaw, v, δ_prev]
  • Control (per step): [Δδ_k, a_k] — steering rate and longitudinal acceleration
  • Horizon: N = 10, dt = 0.1 s, wheelbase L = 0.25 m
  • Dynamics (kinematic bicycle): 
    δ_k    = clip(δ_{k-1} + Δδ_k, ±max_steer)         max_steer = 0.18 rad
v_k    = clip(v_{k-1} + a_k·dt, v_min, v_max)
x_{k+1}  = x_k + v_k·cos(yaw_k)·dt
y_{k+1}  = y_k + v_k·sin(yaw_k)·dt
yaw_{k+1}= yaw_k + (v_k/L)·tan(δ_k)·dt
  • Reference path: generated once on first /odom message — a rectangular loop (0,0)→(8,0)→(8,−4)→(0,−4), 80 samples per edge, 8 passes of a (0.25,0.5,0.25) circular MA, rotated/translated to initial pose, then arc-length parameterized.
  • Cost (per horizon step, summed): 
    J = Σ_k [ qn·e_lat² + qalpha·e_yaw² + qv·(v−v_ref)²
          + qddelta·Δδ² + qac·a²
          + 100·max(0, |v²·tan(δ)/L| − alat_max)² ]
    where e_lat = -sin(yaw_ref)·dx + cos(yaw_ref)·dy and e_yaw = wrap(yaw − yaw_ref).
  • Bounds: Δδ ∈ [±max_dsteer=0.02 rad], a ∈ [a_min, a_max].
  • Solver: scipy.optimize.minimize(method='SLSQP', maxiter=25, ftol=1e-2). The first optimized (Δδ_0, a_0) is applied; resulting δ and v go out as AckermannDriveStamped on /drive at 10 Hz.

Tunable ROS parameters (the ones the LLM is allowed to set):

ParamDefaultAllowed range (clamped in tuner)Meaning
qv10.00–20velocity-tracking weight
qn1.00–100lateral-error weight

Note: tuner clamps a_min/a_max/v_max to tighter ranges than the node's defaults — the tuner will narrow the safe envelope.

How the LLM updates parameters: Out-of-band via the standard ROS 2 parameter service. The tuner shells out to ros2 param set /frenet_mpc_controller <name> <value> (subprocess) — not a topic, not a service the MPC defines, not dynamic-reconfigure, not a file. The MPC node re-reads each parameter on every control-loop tick (get_parameter(...).value), so updates take effect immediately on the next 10 Hz tick.

9. Issues and Observations

Wiring bugs / inconsistencies

  1. Mux output topic mismatch. bringup_launch.py:121 remaps the mux's ackermann_cmd_out to /ackermann_drive, but ackermann_to_vesc_node subscribes to ackermann_cmd (the default). With no remap on the consumer side, the mux's output is not consumed — drive commands would only reach the VESC if /drive is wired some other way (e.g., a stray remap not present in the current launch). Verify with ros2 topic info against a live system.
  2. MPC publishes to /drive, mux config expects drive. mux.yaml lists topic: drive for the navigation input — resolves to the same topic only if the MPC node is launched in the root namespace.
  3. throttle_interpolator disabled. Commented out in bringup. Without it the VESC receives raw, unsmoothed commands from ackermann_to_vesc_node straight to commands/motor/speed. If smoothing is required for hardware safety, this is a regression.

Hardcodes

  1. Hokuyo IP 192.168.0.10 in sensors.yaml — assumes a specific device-side config.
  2. LLM endpoint http://127.0.0.1:8082/completion hardcoded in llm_mpc_tuner_node.py. 120-s HTTP timeout will hang the tuner if the LLM isn't running.
  3. VESC port /dev/sensors/vesc in vesc.yaml — depends on a udev rule that isn't in the repo.
  4. LLM prompt embedded in code (frenet target speed, trajectory shape, etc.) — can't be retuned without editing the node.

Architectural / packaging

  1. Submodule duplication. src/f1tenth_system/ ships its own vesc/ and ackermann_mux/ that shadow the top-level packages. Colcon resolves the top-level ones (confirmed by build/), but the duplicate trees are a footgun. The driver code differs between the two copies (the top-level version has IMU support). Either delete the nested duplicates or pin/document them as read-only references.
  2. llm_mpc_tuner is one-shot. Fires once ~1 s after startup, latches self.done, never tunes again. No feedback from MPC performance back into the LLM, no retry on parse failure.
  3. Subprocess-based parameter setting. llm_mpc_tuner shells out to ros2 param set instead of using rclpy's parameter client — slower and fragile.
  4. Tuner clamps tighter than node defaults. E.g., node default a_max = 10.0 but tuner clamps to [0, 5]. Any LLM-suggested value will narrow the envelope on first run.
  5. /scan is unconsumed. No node in this workspace uses LiDAR data. If LiDAR is intended for obstacle avoidance, the consumer is missing.
  6. Three of four MPC executables are dead code (mpc_node, trajectory_mpc_node, kinematic_mpc_node). The tuner only targets /frenet_mpc_controller.

Metadata / dependencies

  1. Placeholder metadata in mpc_controller/package.xml and llm_mpc_tuner/package.xml: description: TODO, license: TODO.
  2. Missing Python deps (scipy, numpy, requests) — not declared as <exec_depend> and not in any requirements.txt. The MPC and tuner will crash on import on a fresh Humble box without these preinstalled.
  3. vesc_driver.cpp carries an unresolved TODO block (lines ~110-121) about safe off-state and command-bound handling.

Not derivable from code alone: whether the Hokuyo at 192.168.0.10 is reachable from the on-board NUC, whether the udev rule for /dev/sensors/vesc exists on the target host, and whether a local LLM is actually running on :8082 — all of these are deployment-side assumptions the codebase makes implicitly.
